## 一、采购单必须带明细行（阻断项，优先级最高）

### 现状（生产实测 2026-08-03）

| | |
|---|---|
| 采购单总数 | 19 张（存活 11） |
| **带明细行的** | **9 张** |
| **没有明细行的** | **10 张** ← 财务只能看一个单头总额签字，不知道钱花在什么上 |
| 能比对的 9 张里金额对不上的 | 1 张（11%） |

`PO-20260727-001`（连云港中伟塑料制品）明细行合计 ¥7,176 vs 单头 ¥7,020，
**差 ¥156，状态已批准** —— 系统算出了差额，但只显示成一行小字，没拦住。

### 要求

`purchase_order.approval_requested` 与 `purchase_order.placed` **必须**带 `lines[]`。

```jsonc
{
  "event": "purchase_order.approval_requested",
  "data": {
    "purchase_order_id": "uuid",
    "po_no": "PO-20260728-001",
    "supplier_id": "uuid",
    "supplier_name": "伊彤织标",          // 必填：缺了财务无法对账/看付款条件
    "total_amount": 7020,                 // 单头金额
    "currency": "CNY",
    "order_refs": [{ "id": "<synced_order uuid>", "order_no": "QM-...", "internal_order_no": "1022961" }],
    "lines": [                            // ⚠️ 必填，且 Σamount 必须 === total_amount
      {
        "line_id": "uuid",                // 对账锚点，幂等键
        "material_name": "洗标",
        "specification": "50mm 双面",
        "ordered_qty": 1000,
        "ordered_unit": "个",
        "unit_price": 7.02,
        "amount": 7020,                   // 必须 === ordered_qty × unit_price
        "supplier_name": "伊彤织标",       // 行级供应商（同料多供应商时必填）
        "color": "浅蓝", "size": null
      }
    ]
  }
}
```

### 财务侧闸门行为（已上线）

| 校验 | 不通过时 |
|---|---|
| `Σlines[].amount === total_amount` | **禁用「批准放行」**，提示差多少、并要求把差额落成一条具名的扣款/折让行 |
| `lines[]` 为空 | **禁用「批准放行」**：无明细＝财务无从判断钱花在什么上 |
| 供应商对账口径 ≠ 采购订单口径 | **禁用**，并点名是哪几行料对不上 |

**容差：0.01 元。** 老板决策：金额对不上**绝对不能过**，必须改到一致。

> 合法差异（谈好的零头折让）不再"点确认放过" —— 必须由采购落成一条具名的
> 扣款/折让行使总额配平，否则财务只能驳回。差额不再消失在一句"差 ¥156"里。

⚠️ **上线影响**：没有明细行的采购单将无法批准。请优先给在途的 10 张补推明细。

## 二、事件驱动扣款（根治「忘记登记扣款」）

### 设计思路（老板洞察）

> 工厂有扣款，一定是之前有验货的问题？订单补原辅料的问题？
> 这个一定是有事件引发的，所以我们要看看如何通过事件来锁死工厂扣款这个事情。

完全正确。让财务"记得登记扣款"是防不住的 —— 勾选框只能防**忘了填**，
防不住**不知道有**。正确做法是把因果链锁上：

```
验货不合格 / 补料 / 返工  →  财务自动建「待扣款」
                          ↓
          对账/审批时：本单有 N 笔待扣款未处理
                          ↓
              未处理 → 审批闸门卡住（不靠人记得）
```

系统**先于人**知道该扣钱，"忘记"在结构上不可能。

### 需要节拍器推的三个事件

**1. `qc.failed` —— 验货不合格**

```jsonc
{
  "event": "qc.failed",
  "request_id": "om-qc.failed-<uuid>",     // 幂等键
  "data": {
    "event_ref": "QC-20260803-001",        // 节拍器侧验货单号（撤销时用它定位）
    "occurred_at": "2026-08-03T10:00:00+08:00",
    "supplier_name": "某加工厂",            // 必填
    "supplier_id": "uuid",
    "qimo_order_id": "uuid", "order_no": "QM-...", "internal_order_no": "1022979",
    "purchase_order_no": "PO-20260728-001",
    "liable_party": "supplier",            // supplier/factory=工厂担责建扣款；其他值不建
    "amount": 1200,                        // 建议扣款额（财务可改）
    "currency": "CNY",
    "reason": "色差超标 300 件",
    "detail": { "defect_qty": 300, "batch": "B-02", "judgement": "扣款" }
  }
}
```

**2. `material.resupplied` —— 补原辅料**

同上结构。`liable_party` 关键：客户改单导致的补料 ≠ 工厂责任，
此时传非 `supplier` 值，财务侧**不建扣款**（返回 ignored）。

**3. `rework.recorded` —— 返工**

同上结构，`amount` = 向供应商追偿的返工费用。

**4. `deduction.cancelled` —— 事件撤销（误报／复检合格）**

```jsonc
{ "event": "deduction.cancelled",
  "data": { "event_ref": "QC-20260803-001", "reason": "复检合格" } }
```

财务侧把对应的 **pending** 待扣款置 `cancelled`。
已处理（applied/waived）的**不动** —— 钱已经扣了，需人工红冲。

### 财务侧已就绪的部分

| 组件 | 状态 |
|---|---|
| `supplier_deductions` 表（迁移 `20260803_supplier_deductions`） | ✅ 已跑在财务库 |
| webhook 三个事件 + 撤销的处理 | ✅ 已实现（`source_ref` 幂等，重投不重复建） |
| 审批闸门「待扣款已处理」 | ✅ 已实现（未处理即禁用批准） |
| DB 约束：豁免必须写理由、处理必须有真实处理人 | ✅ 已验证（探针测试被正确拒绝） |

**治理红线**：财务侧只建**待处理**记录，`amount` 是节拍器给的**建议值**。
实际扣多少、扣不扣、豁免与否，**必须财务在 UI 确认并记真实 `auth.uid()`** ——
系统不得自主核销财务事项。
